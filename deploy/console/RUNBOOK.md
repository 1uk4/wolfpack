# Wolfpack console on sfo-01 (runbook)

The console (Next.js, `output: standalone`) runs as the `console` user on `127.0.0.1:3200`. `tailscale serve` publishes it on the tailnet over HTTPS at the **origin root**; hubd sits under **`/hub`** on the same origin. Nothing here is applied until the owner approves each step. Written without host access: items marked **UNVERIFIED** are acceptance checks to run on the host, not facts.

Files: `deploy/console/{setup.sh,console.service,console.env.example}`, `deploy/tailscale/serve.sh`, release component `console` (`console/vX.Y.Z` tag, asset `console-vX.Y.Z-linux-x64.tar.gz`), deploy with `infra/release/deploy-release.sh console X.Y.Z`.

## Configuration (`/etc/wolfpack/console.env`, root:root 600, written only if missing)

| Name | Meaning |
|---|---|
| `CONSOLE_HOST` / `CONSOLE_PORT` | bind; the unit refuses anything but 127.0.0.1; port 1024-65535, not 3141/3150 |
| `WOLFPACK_CONSOLE_PUBLIC_ORIGIN` | `https://<host>.ts.net`, required; decides the `__Host-` cookie names (the unit refuses a non-https value) |
| `WOLFPACK_HUB_URL` | where the **server** reaches hubd (today `http://100.120.154.69:3150`) |
| `HUBD_PUBLIC_URL` | `https://<host>.ts.net/hub`, for the `/pair` link and the Devices panel's pairing link. Read **at runtime** (`/api/hub-url`, `src/server/pack/hub-public-url.ts`); `NEXT_PUBLIC_WOLFPACK_HUB_URL` is no longer needed at build time (still honoured as a last fallback) |
| `WOLFPACK_DATA_DIR` | `/var/lib/console/data`: the console's own state (settings, KB graph cache). `setup.sh` creates it `console:console 0700` if missing (the `/var/lib/console` home is created the same way) |
| `WOLFPACK_HEALTH_HUB_URL` | optional; hubd's `/healthz` for pack health. Its origin is also where the restart's live token check goes. Default: the origin of `WOLFPACK_HUB_URL` |
| `WOLFPACK_MACHINE` | optional; the machine this console runs on (default: OS hostname, lowercased, `.local` dropped). The pack panel makes one card per machine: set the same value in `hubd.env` and every `workerd*.env` on the machine (sfo-01: `sfo-01`; the Mac: `mac`). Workers send it in their hub hello, hubd and workerd show it on `/healthz`; one that does not (older build) is grouped by hostname as before. The value is a hostname label (letters, digits, `-`; first dot-label kept, lowercased); anything else is ignored and the hostname is used. It is public on the unauthenticated `/healthz`. `WOLFPACK_HEALTH_HOST_LABELS` renames a machine for display and is keyed by the machine name once a worker reports one (`sfo-01=SFO-01`): re-key any override that used the old host id. |
| `WOLFPACK_HEALTH_WORKERDS` | optional; `<unit>=<url>,...` workerd units to probe (unit `workerd` or `workerd-<x>`). Default `workerd=http://127.0.0.1:7141`. sfo-01: `workerd-wolves=http://127.0.0.1:7143` (set it: without it the default probes a `workerd` unit; the link-only `workerd.service` on sfo-01 is retired and stays disabled since 2026-11-10) |
| `WOLFPACK_HEALTH_WOLVES` | optional; `<name>=<url>,...` wolfd `/healthz` URLs to probe directly. Normally empty: wolves come from their workerd's `/healthz` |
| `WOLFPACK_HEALTH_INTERVAL_MS` | optional; probe interval, default 5000 (minimum 1000) |
| `WOLFPACK_HEALTH_SESSION_TTL_H` | optional; how long a device the hub accepted may restart units while the hub is down, default 72. While the hub is up it is not used: the hub is asked live (see Pack-health restarts) |
| `WOLFPACK_WORKERD_DIRECT_URL` | optional; the local workerd's origin (http on loopback only) for the direct path (see Direct path). Unset: no fallback, the route stays on the hub |
| `WOLFPACK_WORKERD_DIRECT_TOKEN_FILE` | optional; workerd's 0600 direct token. Default `$WORKERD_CONFIG_DIR/direct-token` (`~/.wolfpack/workerd/direct-token`) |
| `WOLFPACK_DIRECT_SESSION_TTL_H` | optional; a browser may use the direct path only if the hub accepted it through this console within this many hours, default 24 |

hubd's own `/etc/wolfpack/hubd.env` gets the same two public values: `HUBD_PUBLIC_URL=https://<host>.ts.net/hub` (pairing QR) and `HUBD_CONSOLE_URL=https://<host>.ts.net` (where the pairing page redirects with `#token=`), then `systemctl restart hubd`.

## Host rollout plan (each step has its own rollback; stop at any step)

**(a) Deploy the console** (not yet reachable from anywhere but the host)
1. Tag `console/vX.Y.Z` on the approved commit (owner pushes; CI builds the linux-x64 tarball).
2. On sfo-01 as root: unpack the release once and `bash console/setup.sh --dry-run setup`, read it, then `bash console/setup.sh setup`. Edit `/etc/wolfpack/console.env` (replace the `CHANGE-ME` host names). `bash console/setup.sh install --bundle console`, then `systemctl start console`.
   Later upgrades: `infra/release/deploy-release.sh console X.Y.Z` (verifies sha256, installs, health = unit active + HTTP 200 on `/api/health` or `/` from localhost, auto-rollback).
3. Check: `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3200/` is 200; `ss -ltn | grep 3200` shows 127.0.0.1 only.
- Rollback: `systemctl disable --now console`; or `bash /opt/wolfpack-console/setup.sh rollback`; full removal `setup.sh uninstall` (add `--purge` for user, state and env). No other system is changed by this step.

**(b) `tailscale serve`** (tailnet only; never `funnel`)
1. `tailscale version`, `tailscale serve --help` (confirm `--bg --https --set-path` exist; HTTPS needs MagicDNS + HTTPS certificates enabled in the tailnet admin console, owner action).
2. `bash deploy/tailscale/serve.sh --dry-run on`, then `... on`, then `... status`. The routes: `/hub` → `http://100.120.154.69:3150` and `/` → `http://127.0.0.1:3200`.
3. Acceptance from a tailnet device (all **UNVERIFIED** until run):
   - `curl -sI https://<host>.ts.net/` → 200 from the console.
   - `curl -s -o /dev/null -w '%{http_code}' https://<host>.ts.net/hub/v1/wolves` → 401 (hubd answered; the `/hub` prefix was stripped, since hubd has no `/hub/...` routes).
   - **`/hub/pair` with no trailing slash** returns hubd's pairing page (200). Expected: serve matches `/hub` as a path prefix and forwards `/pair`. hubd's page computes its POST URL from `location.pathname` (`/hub/pair` → `/hub/v1/pair`), so it works with the prefix stripped, with or without a trailing slash (pinned by `hubd.pairpage.test.ts`). If bare `/hub/pair` is not forwarded as `/pair`, fall back to a trailing-slash link and say so here.
   - **SSE `/hub/v1/events`** (`curl -N -H 'Authorization: Bearer <token>' https://<host>.ts.net/hub/v1/events`): the same stripping applies; also confirm events arrive as they happen, not in a buffered burst. tailscale serve is a Go reverse proxy that streams `text/event-stream`; **UNVERIFIED**. The worker link (`/hub/v1/link`, WebSocket) is likewise untested through serve; it matters only for step (d).
4. Add the public values to `hubd.env` (see above) and restart hubd.
- Rollback: `bash deploy/tailscale/serve.sh off` (removes only these two routes; never `serve reset`); revert the two `hubd.env` lines and restart hubd. The tailnet-IP hubd keeps working throughout.

**(c) Pair the owner's phone over HTTPS**
1. On sfo-01: `hubd pair --kind browser` (prints a QR/link built from `HUBD_PUBLIC_URL`), or Settings → Devices → "Add device" in an already-paired console (its link comes from `HUBD_PUBLIC_URL` at runtime).
2. Phone on the tailnet opens the link, pairs, lands on `https://<host>.ts.net/pair#token=…` → stored → home. Check Settings → Devices shows the phone.
- Rollback: revoke the device (Settings → Devices, or `hubd devices revoke`). No infrastructure change.

**(d) Mac workerd link** (only if wanted)
Nothing has to move: the Mac's workerd links to `http://100.120.154.69:3150`, which stays valid while hubd keeps its tailnet bind. Move to `https://<host>.ts.net/hub` only if you want TLS on the link or are about to do (e); it needs the WebSocket upgrade through serve (**UNVERIFIED**, test with `wscat`/workerd against a throw-away device first). Change the hub URL in the Mac workerd config (`hub.json`, restart workerd). 
- Rollback: set the URL back to `http://100.120.154.69:3150`, restart workerd.

**(e) "Close hubd's public port"**
"Public" needs care: hubd binds the **tailnet IP** `100.120.154.69:3150` (`HUBD_HOST`), not `0.0.0.0` (the unit refuses wildcards), so it is not on the public internet. It is reachable by every device the tailnet ACLs allow, over **plain HTTP** (tailnet traffic is WireGuard-encrypted, so not cleartext on the wire). After (b) it is also reachable at `https://<host>.ts.net/hub`. To check what else is exposed, on the host: `ss -ltnp` (expect 3150 on the tailnet IP, 3200 on 127.0.0.1, sshd, nothing on `0.0.0.0` that you did not choose) and `tailscale serve status` / `tailscale funnel status` (funnel must be empty). Firewall state on sfo-01 was not inspected.
- Recommendation: **do not move hubd to 127.0.0.1 in this phase.** What would break if you did (`HUBD_HOST=127.0.0.1`, restart hubd, and serve upstream `http://127.0.0.1:3150` via `serve.sh on --hub-upstream http://127.0.0.1:3150`):
  - the Mac's workerd (links to the tailnet IP) → must move to `https://<host>.ts.net/hub` first (step d, needs the WebSocket check);
  - workerd on sfo-01 (and `workerd-wolves`, wolfd links, anything with `hubUrl` = the tailnet IP in `hub.json`) → change to `http://127.0.0.1:3150` and restart;
  - the console's `WOLFPACK_HUB_URL` → `http://127.0.0.1:3150`;
  - any phone/browser or script using `http://100.120.154.69:3150` directly.
  Do it only after all links are listed and moved, one at a time (hub.json edits, restart, confirm the link is up in the console), hubd last.
- Rollback: `HUBD_HOST=100.120.154.69` in `hubd.env`, restart hubd, point the links back (`serve.sh on --hub-upstream http://100.120.154.69:3150`).

## Operate

- Logs: `journalctl -u console -n 100 --no-pager`. Restart: `systemctl restart console`. Roll back to the kept previous release: `systemctl start wolfpack-rollback@console` (or `bash /opt/wolfpack-console/setup.sh rollback`).
- Health: `curl -s http://127.0.0.1:3200/api/health`: a JSON snapshot of hubd, the workerd units and the wolves, probed by the console itself (no hub call, so it answers with hubd stopped or frozen). Always 200 while the console runs. Live: `GET /api/health/stream` (SSE).
  **Changed:** `/api/health` no longer answers 503 when the hub is down. It is always 200 with a per-link snapshot, so an external monitor keyed on 503 must read `links[]` instead (e.g. `jq -e '.links[] | select(.id=="hubd") | .status=="ok"'`). Each link's `error` is a short code (`timeout`, `refused`, `http_<status>`, `wrong_service`, `bad_body`, `unreachable`, `slow`, `reports_not_ok`, `wolf_<state>`, `workerd_unavailable`, `not_reported`); the raw error is only in the console's journal (`journalctl -u console | grep 'console: health'`).

## Direct path (hub down)

With `WOLFPACK_WORKERD_DIRECT_URL` set, a console on the same machine as a workerd falls back to that workerd's loopback-only `/direct/v1` while hubd is unreachable (details: `apps/console/src/server/pack/direct-path.ts`).

- **When it switches:** after 2 consecutive pack-health rounds in which hubd does not answer while the direct link does; back to the hub after 2 answering rounds. A hub call that gets no answer runs one live round (debounced to one per 2 s). So a live hub failure goes direct after 2 failed rounds: a live check plus the next 5 s round (`WOLFPACK_HEALTH_INTERVAL_MS`), or two live checks at least 2 s apart. Until then requests fail with the retryable "hub is unreachable" error. This is deliberate, to avoid flapping.
- **What it serves:** chat, threads, streams and reads of the local workerd's wolves, and `restartWolf` (recovery). Not served (retryable "hub is unreachable"): other hosts' wolves, hub-only routes (work, KB, devices, hub events), and `putWolfSettings`, `putPrompt`, `resetPrompt`, `revealWolfSetting`, `putThreadSettings`.
- **Exposure:** workerd refuses `/direct*` from a non-loopback peer and from requests carrying forwarding headers (`X-Forwarded-*`, `Forwarded`, `Via`). A raw TCP forward to 127.0.0.1 (e.g. `tailscale serve --tcp`, `socat`, `ssh -L`) adds no headers and looks like loopback, so only the token protects that case. **Never set one up to workerd's port.**
- **Token file:** created by workerd (0600). A symlink or a file owned by another user is refused; an empty or invalid file of workerd's own is replaced with a fresh token.

## Pack-health restarts (polkit)

`POST /api/health/restart {"service":"hubd"|"workerd"|"workerd-wolves"|"wolfd@<name>"}` runs `systemctl --no-ask-password --no-block restart <unit>.service` (argv, no shell) as the `console` user. The permission is the polkit rule `deploy/console/50-console-restart.rules`: user `console` may **restart** `hubd`, `workerd*` and `wolfd@<name>` and nothing else (no start/stop, no other unit). Polkit rather than sudoers because the unit runs with `NoNewPrivileges=yes`, which makes sudo unusable; polkit asks PID 1 over D-Bus, the same mechanism `workerd-wolves` already uses for `wolfd@` (infra/wolves/50-workerd-wolves.rules).

- Install (part of `setup.sh setup`, owner approval first): `install -o root -g root -m 0644 deploy/console/50-console-restart.rules /etc/polkit-1/rules.d/` (polkit reloads rules by itself). Needs polkit (`/etc/polkit-1/rules.d`); present on sfo-01 since H5.
- Check (as root): `runuser -u console -- systemctl --no-ask-password restart hubd.service` works; `runuser -u console -- systemctl --no-ask-password stop hubd.service` and `... restart ssh.service` are refused (**UNVERIFIED** until run).
- The console allows a name only if it is a link it knows (hubd, a configured workerd unit, a wolf a workerd reported); one restart per service per 60 s (429 + `Retry-After`). The live checks are capped across all callers: at most 2 in flight (beyond: 429, `Retry-After: 5`) and 30 per minute (beyond: 429 until the window frees a slot). Auth: `Authorization: Bearer <device token>`, decided by the hub whenever it can:
  - **Live check first, always** (whatever pack health currently shows for hubd): the console checks the bearer with `GET <hub>/v1/wolves` using that same token, 3 s timeout. `<hub>` is the same hub pack health probes (the origin of `WOLFPACK_HEALTH_HUB_URL`, else of `WOLFPACK_HUB_URL`, else `127.0.0.1:3150`, plus `WOLFPACK_HUB_URL`'s path prefix). 2xx allows it. 401, 403 or any other 4xx except 408/429 refuses it and drops the token from the witness, so **a device revoked on the hub loses restart rights immediately while the hub answers** (hubd answers 401 for a revoked token).
  - **No verdict** (408, 429, 5xx, network error, timeout): only then the session witness decides. The bearer must have been accepted by the hub through this console within `WOLFPACK_HEALTH_SESSION_TTL_H` (default 72 h; SHA-256 hashes only, in `$WOLFPACK_DATA_DIR/health-sessions.json`, mode 0600). So **a device revoked while the hub is down keeps restart rights for at most 72 h** after its last successful hub call. To cut that short: `rm $WOLFPACK_DATA_DIR/health-sessions.json && systemctl restart console` (every device then needs the hub up once more before it can restart anything). Every attempt is logged: `journalctl -u console | grep 'health restart'` (device = first 12 hex of the token's SHA-256).
- Rollback: `rm /etc/polkit-1/rules.d/50-console-restart.rules` (restarts then answer 502; health reads are unaffected).
## Pack-health logs and rollback (work-wolfpack-yM3uTlj)

The modal's per-service **Logs** and **Roll back** go through this console server only (never a wolf, never the hub). Same auth as restart (live hub check, 72 h witness fallback, the same 2-in-flight / 30-per-minute caps).

**Logs**: `GET /api/health/logs?service=<id>&lines=<n>` (n 1-200, default 100; `<id>` must be a unit the console may restart). Runs `journalctl -u <unit>.service [-u wolfpack-rollback@<unit>.service] -n <n> -o short-iso --no-pager` (argv, 15 s timeout, at most 2 at once). Lines are redacted (Bearer/Basic values; every value of a `Cookie:`/`Set-Cookie:` header; known token prefixes such as `sk-`, `ghp_`, `github_pat_`, `xox?-`, Telegram `<id>:<secret>`, JWTs, even when short; `*token|*key|*secret|*password|authorization` `=`/`:` values; runs of 33+ token characters that look random. Plain 40-hex git shas and 64-hex sha256 digests are kept) and the newest lines are kept within 64 KiB. Logged: `journalctl -u console | grep 'health logs'`.
- Needs journal read access for the `console` user. `console.service` now has `SupplementaryGroups=systemd-journal` (no `ReadWritePaths` or polkit change: journalctl reads `/var/log/journal` and `/run/log/journal`, which `ProtectSystem=strict` leaves readable). Without it the endpoint answers `502 journal_denied`, never an empty log. Output past 4 MiB answers `502 too_large` (ask for fewer lines).
- **Caveat: `systemd-journal` is the whole journal.** With that group a compromised console process can read every unit's journal, including sshd/auth and every `wolfd@` wolf's output, not just the units the modal shows. The real limit is the allowlist in `createLogReader` (apps/console/src/server/pack/pack-actions.ts: only units `health.restartable()` names, argv only, no free-form `-u`); it must stay. Redaction is a second line, not the boundary.

**Roll back**: `POST /api/health/rollback {"service":"hubd"|"workerd"|"console"}` runs `systemctl --no-ask-password --no-block start wolfpack-rollback@<svc>.service`. One per service per 10 min. **Owner-initiated only**: nothing in the console, hubd or workerd starts it on its own (self-healing is restart only).
- `wolfpack-rollback@.service` is a root `Type=oneshot` unit running `/usr/local/lib/wolfpack/console-rollback-release.sh <svc> --rollback`: the console bundle's own copy of `infra/release/deploy-release.sh`, installed under its own name so it never overwrites a shared `/usr/local/lib/wolfpack/deploy-release.sh`. Same per-component lock as a deploy, then the installed `/opt/wolfpack-<svc>/setup.sh rollback` (swap `current`/`previous`, restart if active). If that setup.sh refuses (e.g. the previous release has no `server.js`/`workerd.mjs`), the refusal stands: nothing is swapped behind it (exit 1). The links are swapped by hand only when there is no installed setup.sh. Then the unit must be active and stable across a settle. Exit 0 ok, 1 refused / nothing changed, 2 usage, 4 changed but unhealthy or half-done (needs a person). It never deploys or downloads anything. The unit uses `AssertPathExists=` for the script and `previous`, so a missing one fails the start (`Result=assert`) instead of skipping it quietly.
- Why a unit and not sudo or a setuid helper: the console runs with `NoNewPrivileges=yes`, so sudo cannot work, and widening the console's own rights would let a compromised console do anything root can. A templated oneshot keeps the root code fixed (the script on disk, root-owned) and the console's only input the instance name, which polkit pins to exactly `hubd|workerd|console`; the script validates it again. Running in its own unit also means rolling back the console (which restarts `console.service`) cannot kill the rollback half-way.
- The modal shows Roll back only where `/opt/wolfpack-<svc>/previous` exists and differs from `current`, and names the target version (`previous/VERSION`). The result shows through the snapshot (the service's version changes and it comes back; the console row's page reconnects). Output: the row's Logs (includes `wolfpack-rollback@<svc>`), or `journalctl -u wolfpack-rollback@hubd`, and `/var/log/deploy-release.log`.
- The modal reads each rollback unit's last run (`systemctl show wolfpack-rollback@<svc>.service -p Result,ExecMainStatus,ActiveState,ExecMainExitTimestamp,AssertResult,AssertTimestamp`, argv, 3 s timeout, cached 5 s; snapshot `actions.rollback[].last = {result, exitStatus, at}`). "Rollback started" ends when that unit finishes. A start refused by `AssertPathExists` (script missing) never runs, so only `AssertResult=no` and `AssertTimestamp` move; the modal reports that as "rollback script or previous release missing on the host". A failure shows as e.g. "Rollback failed (exit 4: needs a person) — see Logs"; a success clears once the service reports another version.
- Roll back is hidden when the kept `previous` is newer than `current` (X.Y.Z compare): after a rollback, `previous` is the release just left. To go forward again, deploy it (`deploy-release.sh <svc> <X.Y.Z>`). Same X.Y.Z with another build: offered, and the confirm names the build (`v0.1.18+a`). An unreadable VERSION: still offered, and the confirm says the version is unknown.
- workerd here means the link unit `workerd.service` only (`/opt/wolfpack-workerd/current`). `workerd-wolves` runs from its own `/opt/wolfpack-workerd-wolves/current`, so a workerd rollback does NOT change it, even at its next restart: the two can then run different versions. Each workerd row in the modal shows its own `v<version>` from `/healthz`, so a mix is visible. List `workerd-wolves` in `WOLFPACK_HEALTH_WORKERDS` to see it. Wolves and `workerd-wolves` are not rolled back from the modal.

**Enable on sfo-01** (owner, as root; nothing here is applied by an agent). From an unpacked console release that has these files (or the repo checkout):
1. `install -d -m 0755 /usr/local/lib/wolfpack && install -o root -g root -m 0755 console/deploy-release.sh /usr/local/lib/wolfpack/console-rollback-release.sh` (the console's own copy; leave any `/usr/local/lib/wolfpack/deploy-release.sh` alone). 5. Check: (a) `grep ^Groups /proc/$(systemctl show console -p MainPID --value)/status` lists the gid of `getent group systemd-journal`; (b) `systemd-run --quiet --wait --pipe -p User=console -p SupplementaryGroups=systemd-journal journalctl -u hubd -n 3 --no-pager` prints hubd lines (`runuser -u console -- journalctl ...` always fails here, because runuser does not apply the unit's `SupplementaryGroups=systemd-journal`); `runuser -u console -- systemctl --no-ask-password start wolfpack-rollback@ssh.service` is refused; `ls -l /opt/wolfpack-{hubd,workerd,console}/previous` shows what a rollback would go back to. A real rollback test is optional: `systemctl start wolfpack-rollback@console` then `deploy-release.sh console <newer X.Y.Z>` to return.
- Rollback of this change: `rm /etc/systemd/system/wolfpack-rollback@.service /usr/local/lib/wolfpack/console-rollback-release.sh`, restore the previous `50-console-restart.rules`, drop `SupplementaryGroups=` from `console.service`, `systemctl daemon-reload && systemctl restart console`. Logs then answer 502 journal_denied and Roll back 502.

- Release layout: `/opt/wolfpack-console/{releases,current,previous}`, 5 releases kept.
- The console is served at the origin root only (absolute `/api/...` URLs, no `basePath`).
