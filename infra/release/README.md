# wolfd release tarball (H3)
    scripts/build-wolfd-release.sh [--arch x64|arm64] [--out DIR] [--with-cli]   # Docker; default x64 (DO droplet) -> dist-release/wolfd-<ver>-linux-<arch>.tar.gz
    scripts/smoke-wolfd-release.sh dist-release/wolfd-*-linux-x64.tar.gz          # clean node container, npm/npx tripwired, launch.sh, GET /v1/wolves
    wolfpack sync <wolf> --release <tarball>                                       # wolf with runtime: wolfd -> PUT /wolves/:id/bundle {runtime:"wolfd", tarball, models, env}

Contents: `packages/*/{package.json,dist}`, prod `node_modules` (harness workspace closure, glibc SDK native pkg only), `launch.sh`, `wolfd.service`
(template: @USER@ @HOME@ @RELEASE@ @MEMORY_MAX@ @NAME@; hardened, generated from infra/wolves/wolfd@.service), `templates/{wolf.yaml,models.json,.env.example}`, `tools/bin/claude` (-> the SDK's native binary),
`tools/install-claude-cli.sh` (pinned claude-code, optional), `VERSION`. Never a `.env` (the build fails if one is present).
Agent: unpacks to `<wolf home>/release` (previous kept as `release.prev`), `agent/launch.sh` execs `release/launch.sh`.

## Memory and KB through the hub (H6)
A VPS wolf has no Syncthing. With `WOLFPACK_HUB_KB=1` in its `.env`, wolfd syncs the KB itself from hubd into `<home>/kb-mirror` and feeds `<home>/ops/inbox/<wolf>/*.md` to hubd `POST /v1/contributions` (`packages/harness/src/wolfd/hub-kb.ts`). `.env` keys: `WOLFPACK_HUB_KB`, `WOLFPACK_HUB_URL`, `WOLFPACK_HUB_TOKEN` (a worker token of the wolf's host), `WORK_ENDPOINT=<hub>/v1/workapi`, `WORK_TOKEN` (the same token). wolf.yaml needs `domains: [...]` (must match the registry), `extensions: [memory]` (the memory bundle also carries the tasks tools) and `memory.live: true`. The memory bundle goes to `<home>/den/extensions/wolfpack-memory/index.js` (build it with `buildDurableExtension("memory", dir)` from `packages/cli/dist/bundle.js`).
Work API: hubd serves a host-scoped proxy at `/v1/workapi/work` (`packages/hubd/src/work-proxy.ts`). **On sfo-01 the hubd sandbox keeps `domains/*/work` read-only (RUNBOOK.md, `setup.sh` without `--hub-writes`), so only the proxy's reads work there; a create/patch fails with EROFS** (`open .../domains/<d>/work/<id>.md.tmp-...`) after the ledger event is already appended, leaving a ledger-only item. The graduation preview itself only reads work items (its one write is the token file `<den>/tasks/graduation/<token>.json`); it is proven by `infra/tracer/run-tracer.sh --kb`, not on sfo-01.
A new wolf needs its contribution lanes first (`install -d -o wolf-W1hOrJ -g wolf-W1hOrJ -m 0777 .../librarian/{inbox,receipts}/<wolf>`). Keep a contribution's `domain_hint` to a real KB domain: Dewey parks one for an unknown domain (EACCES on `mkdir domains/<hint>/entries`).
`wolfpack sync <wolf> --release` does not reach workerd-managed wolves yet (agent 404). Use `wolfpack deploy` (below): it talks ssh to the host, not the agent, so it works for workerd-managed wolves. It does not fix `sync` itself (that still 404s).

## Deploying a published release: `wolfpack deploy` (C3)
The host downloads a GitHub release itself (`<component>/vX.Y.Z`, see release.yml), verifies it, switches, health-checks and rolls back on failure.
    wolfpack deploy <wolf> --release wolfd/v0.1.2 [--host sfo-01] [--dry-run] [--health-timeout 60]     # --release takes wolfd/vX.Y.Z | vX.Y.Z | X.Y.Z
    wolfpack deploy --component hubd|workerd --release hubd/v0.2.0 --host sfo-01 [--dry-run]
The CLI pipes `infra/release/deploy-release.sh` over ssh (`sudo bash -s -- ...`; nothing is left on the host) and streams its output. Host: `--host`, else the one registered host whose wolves tree has the wolf, else the default host. Exit codes: 0 ok or no-op, 1 refused (nothing changed), 3 failed health check and rolled back (unit healthy again), 4 rollback unhealthy (needs a human).
Script (`deploy-release.sh <wolfd|hubd|workerd> <X.Y.Z> [--wolf n] [--dry-run]`, root, needs only bash curl sha256sum GNU-tar systemctl): all code is in `main()` so it is safe to pipe to `bash -s`; SIGHUP/SIGPIPE are ignored and output is tee'd to `/var/log/deploy-release.log`, so an ssh drop does not stop a half-done switch. Order: `--wolf` (<= 27 chars) and the Linux user are checked first; the wolf home must be a real dir owned by `wolf-<n>`; the wolf's `.env` must not set `ANTHROPIC_API_KEY` (name only reported); **recovery**: if `release` is missing (an earlier run died mid-switch) it is restored from `release.prev` (else the newest `release.prev-*`) and leftover `.release.new.*` / `.deploy-stage-<n>.*` are removed; then `curl --proto =https --tlsv1.2 --max-time 120` into a fresh `mktemp -d`; refuse on a missing/malformed/mismatching `.sha256`, one naming another component, an unsafe tar member or a VERSION that is not the requested one. Tar policy (GNU tar listing): devices/fifos/sockets, absolute or `..` member names, escaped/odd names, non-canonical names (`//` or a `.` component after one leading `./`), members written beneath a symlink, link members whose name contains a space, and any listing line with more than one ` -> ` / ` link to ` separator are refused; **links are validated, not banned**, because the real wolfd tarball contains 31 relative symlinks (`node_modules/.bin/x -> ../x/y`, all with `..`) and a hardlink (`esbuild`): a symlink must be relative and resolve inside the tree, a hardlink must name an EARLIER regular member of the same archive. After extraction every symlink is canonicalised (`readlink -m`, so dangling-but-inside links are fine) and must stay under the extraction dir (catches chains that are lexically inside but really escape). The real `wolfd/v0.1.1` tarball is accepted (`DEPLOY_PROOF_REAL=<tarball> infra/release/deploy-proof.sh` checks it). Extraction is `--no-same-owner --no-same-permissions --no-overwrite-dir` into a root-owned 0700 staging dir (same filesystem as the wolf home), then `chown -R -h wolf-<n>` (a wolf home on a different filesystem than `/home` is refused: no staging inside the wolf-writable home), `chmod -R u-s,g-s`, VERSION check - **all before the first rename**. Switch (every rename checked): `release.prev` -> `release.prev-<X.Y.Z|unknown>-<ts>`, `release` -> `release.prev`, staged -> `release` (all `mv -T`). After a good deploy only the newest 2 `release.prev-*` and 2 `release.failed-*` are kept: selection is a bash glob with the strict name `^release\.(prev|failed)-[0-9A-Za-z.]+-[0-9]{8}T[0-9]{6}Z$`, real dirs only, ordered by the timestamp in the name (never `ls`/mtime), removed with `rm -rf --one-file-system`; recovery uses the same selection; restart `wolfd@<n>`. Healthy = unit active, serving line `wolfd: <n> serving unix:/run/wolfd-<n>/serve.sock` in THIS invocation's journal (`_SYSTEMD_INVOCATION_ID`), `-p err` empty, InvocationID and NRestarts unchanged across `--settle` (default 6 s, longer than RestartSec=5, so a crash loop fails). On failure the failed dir is kept as `release.failed-<ver>-<ts>`, the previous release is swapped back, restarted and re-checked. Same version already running = no-op, no restart (warns if the unit is not active). A per-component/wolf `flock` (`/run/deploy-release-<comp>-<wolf|host>.lock`) refuses a concurrent deploy. Test seams (`DEPLOY_BASE_URL`, `DEPLOY_SYSTEMCTL`, `DEPLOY_TMP`, `DEPLOY_LOCK_DIR`, ...) are honoured only with `DEPLOY_TEST=1`; otherwise the URL is fixed to GitHub and temp is `/tmp`. Exit codes: 0 ok/no-op, 1 refused (nothing changed), 2 usage, 3 failed and rolled back, 4 rollback unhealthy / manual recovery needed (the CLI maps 255 to "ssh failed").
hubd/workerd: same download/verify/inspect/VERSION steps, then the release's `setup.sh install --bundle`. `was_active` and the unit's InvocationID are recorded first; if the service was active and the InvocationID did not change after install, the new release is not running and the deploy takes the rollback path; if install fails and `current` did not change, exit 1 (nothing to roll back); if it changed (even with a failing install) the health check / rollback path runs. Rollback uses the `setup.sh` saved at `/opt/wolfpack-<comp>/setup.sh` by the last successful deploy, or swaps `current`/`previous` itself when there is none, then restarts explicitly (the real `setup.sh rollback` only restarts an active service). A service that was stopped before the deploy is installed and reported, not failed. Health = active, InvocationID/NRestarts stable, no err journal, and the port in `/etc/wolfpack/<comp>.env` (`<COMP>_HOST/_PORT`) accepts a connection. First-time `setup.sh setup` is still by hand; `deploy` only upgrades. Follow-up (not in this ticket): make `release` a symlink flip so the switch is one atomic rename.
Proof: `infra/release/deploy-proof.sh` (Docker, native arch; synthetic releases with the real URL layout from a local http server; the script is fed via `bash -s < deploy-release.sh` exactly like the CLI; systemctl/journalctl are doubles, so it proves the script logic, not systemd) prints `DEPLOY PROOF OK`.

## hubd and workerd upgrades (C4)
`deploy` only UPGRADES. If `/opt/wolfpack-hubd/current` (or `/opt/wolfpack-workerd/current`) is missing it refuses (rc 1) and points at `setup.sh setup`; a first install is an owner step: unpack the release, `bash <comp>/setup.sh setup ...`, then `install --bundle`.

**workerd has two units on sfo-01, with separate installs.** `deploy/workerd/setup.sh` only knows the link-only `workerd.service` (`/opt/wolfpack-workerd`, `/etc/wolfpack/workerd.env`, port 7142). `workerd-wolves.service` (infra/wolves) has its own dir `/opt/wolfpack-workerd-wolves` (`releases/`, `current` -> `releases/<id>`, `previous`; the same `workerd.mjs` plus `wolfd-unit.sh`), env `/etc/wolfpack/workerd-wolves.env` (port 7143), and setup.sh does not manage it.
`deploy-release.sh workerd` takes `--unit link|wolves|both`. **The default is `link`** (`auto` means `link`); `wolves` and `both` restart workerd-wolves and are opt-in. The log's first lines name the unit set.
- Order: the link unit goes first (the release's `setup.sh install`, then its health check). Only if it is healthy does the wolves unit follow: the script installs `workerd.mjs/RUNBOOK.md/VERSION` into a new release dir itself, smoke-tests it, flips `current` (old -> `previous`), restarts the unit and health-checks it.
- Rollback: if either fails, every unit whose release actually CHANGED is rolled back (swaps done independently), then restarted (`reset-failed` first) and re-checked. A unit that did not change (install failed, never reached) is never restarted. rc 3 = rolled back and healthy, rc 4 = needs a human (a failed swap/restart/health, or a survival failure).
- Health per unit: active, same InvocationID/NRestarts across `--settle`, no `-p err` journal, port from its env file accepts a connection (retried ~5 s).
- **Supervised-wolf survival (workerd-wolves restarts only).** Old Hal and Dewey run in their own units (`wolf-ETAy7b.service`, `wolf-W1hOrJ.service`) and hal2 is `wolfd@hal2.service`; none lives in workerd-wolves's cgroup, which holds only `workerd.mjs`, `wolfd-unit.sh` and its `sleep`. Before touching it the script (a) runs `systemd-cgls -u workerd-wolves.service` and REFUSES (rc 1, nothing changed) if any other process is in the cgroup (a restart with KillMode=control-group would kill it), and (b) snapshots (preflight, then retaken right before the restart, after the link unit settled; a failing `list-units` or an empty snapshot refuses) every active `wolfd@*.service` and `wolf-*.service` with InvocationID and MainPID. After the restart, and after any rollback restart, the same units must be active with unchanged IDs (checked again after the wolves health check); otherwise rc 4 (`setup.sh` is still saved) and **no further automatic restarts or rollback**. A restart of workerd-wolves should therefore not interrupt Hal/Dewey/hal2; the proof checks that.
- `wolves_install` refuses unless `/opt/wolfpack-workerd-wolves`, its `releases/` and the live release are root-owned real directories (not symlinks) and `current` is a symlink into `releases/`. It carries `wolfd-unit.sh` over from the live release only if that is a regular non-symlink file. **The release tarball never ships `wolfd-unit.sh`, so a fix to `infra/wolves/wolfd-unit.sh` cannot arrive through `deploy`**; the CLI passes the sha256 of its checkout's `infra/wolves/wolfd-unit.sh` (`--wolfd-unit-sha256`) and the host warns when the live copy differs (without the CLI compare `sha256sum` by hand). A failed flip removes the new release dir; old releases are pruned only after a successful deploy.
- `--unit wolves|both` is refused (rc 1, nothing written) when `/opt/wolfpack-workerd-wolves` is missing or its `current` is not a symlink. `--unit` is rejected (rc 2) for wolfd and hubd.

**hubd health:** hubd has no health route. After the unit/port checks the script sends an unauthenticated `curl --noproxy '*' GET /v1/wolves` (retried ~5 s) and accepts only HTTP 401 (every route except `POST /v1/pair` answers 401 before 404, so a 401 proves the HTTP app is up). The host form must be an IPv4 address or `localhost`, otherwise the probe is skipped with a log line; a missing curl is logged too. Such a 401 does not count against hubd's rate limiter (it only counts failed `POST /v1/pair` redemptions) and writes no ledger/audit entry (attribution is on ledger events of writes). Change the probe if hubd gains a real `/health`.
