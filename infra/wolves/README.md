# Supervising workerd for VPS wolves (H4)

Two units, next to (never replacing) the link-only `deploy/workerd/workerd.service` (verified untouched):

| unit | what |
|---|---|
| `workerd-wolves.service` | **not** link-only workerd; user `workerd-wolves`; state `/var/lib/workerd-wolves`; env `/etc/wolfpack/workerd-wolves.env` (`WORKERD_PORT=7143`, `WORKERD_FEED`); bundle `/opt/wolfpack-workerd-wolves/current/` (workerd.mjs + `wolfd-unit.sh`). Name says what it does and keeps every path (unit, user, state, env, port, bundle) disjoint from `workerd` (7142). |
| `wolfd@.service` | one instance per wolf: `User=wolf-%i`, `EnvironmentFile=/home/wolf-%i/.env` (600), `MemoryMax=700M` (+`MemoryHigh=600M`, `MemorySwapMax=0`), `WOLFPACK_SUBAGENT_HOST_MAX=3`, hardening below, `Restart=on-failure` + `StartLimitBurst=5/300s`, guards (`.env` mode 600, no `ANTHROPIC_API_KEY`) then `release/launch.sh` (which repeats the key/token guards). |

## Mechanism chosen: (a) per-wolf template units, started through systemd
workerd cannot raise privilege (`NoNewPrivileges`, empty capability set, no `CAP_SETUID`). It asks **systemd** (PID 1, which already knows how to switch user, apply a cgroup, `EnvironmentFile`, sandbox) to run `wolfd@<name>`; a polkit rule (`50-workerd-wolves.rules`) lets `workerd-wolves` start/stop/restart `wolfd@<name>.service` and nothing else. Why not the others: (b) `systemd-run --uid` needs the same privilege and re-states the whole sandbox on a command line; (c) `CAP_SETUID/SETGID` on workerd would give a network-facing process the power to become *any* user, and gives no per-wolfd MemoryMax (children stay in workerd's cgroup).
Per-wolfd `MemoryMax` is real because each wolfd (and its claude children) is its own unit/cgroup.

Wiring (smallest code change): workerd's existing `--wolfd <cmd>` spawns `wolfd-unit.sh --config <registry>/<name>/wolf.yaml --socket <sock>`, a small supervised child that does `systemctl start wolfd@<name>`, waits for the socket, prints `serving unix:<sock>`, watches the unit and exits non-zero when it is dead (workerd's backoff re-runs it). SIGTERM to it leaves the unit running; a restarted workerd **adopts** the live wolfd from its socket (existing orphan-adoption). The only TypeScript changes: `--wolfd-transport socket|tcp` / `WORKERD_WOLFD_TRANSPORT` (opt-in; default unchanged; rejected with `--link-only`), and the stale-socket removal in `Supervisor.adoptOrSpawn` is now best-effort (found by the simulation below: with a socket in a dir owned by another user it threw EACCES and **crashed workerd**).

The wolf registry is `/etc/wolfpack/wolves/<name>/wolf.yaml` (root-owned, `name` + `serve.socket: /run/wolfd-<name>/serve.sock` only). The real config is `/home/wolf-<name>/wolf.yaml`, unreadable by workerd. The socket lives in `RuntimeDirectory=wolfd-<name>` (0750, group `wolf-<name>`, `UMask=0007`); `provision-wolf.sh` adds `workerd-wolves` to the group `wolf-<name>`, so only workerd can dial it. workerd's own `<den>/logs/wolfd.log` write (den = registry dir) fails silently: logs are in the journal (`journalctl -u wolfd@<name>`).

## Sandbox
wolfd@: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=tmpfs` + `BindPaths=/home/wolf-%i` + `ReadWritePaths=/home/wolf-%i` (each wolf sees **only its own home**, `/home/<other>` does not exist for it), `PrivateTmp`, `PrivateDevices`, `Protect{KernelTunables,KernelModules,KernelLogs,ControlGroups,Clock,Hostname}`, `ProtectProc=invisible`, `ProcSubset=pid`, `Restrict{SUIDSGID,Namespaces,Realtime}`, `LockPersonality`, empty `CapabilityBoundingSet`/`AmbientCapabilities`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `SystemCallFilter=@system-service`, `TasksMax=256`. No `MemoryDenyWriteExecute` (node JIT).
workerd-wolves: the same set as the link-only unit (`ProtectHome=yes`, strict, only `/var/lib/workerd-wolves` writable, `AF_NETLINK` kept for `os.networkInterfaces()`); it needs just AF_UNIX to the system bus. **Not tested under the real seccomp filter: the claude native binary and `@system-service`** (no systemd available here, see below); first thing for H5 to try, with `journalctl -k`/`SystemCallLog=` if it dies with EPERM.

## MemoryMax and the 2 GB / 1 CPU host
Measured: hubd ~105, workerd ~105, wolfd ~190 idle (~440 with one claude child), +250 MiB per extra concurrent claude. `MemoryMax=700M` per wolf = wolfd + ~2 claude children; `WOLFPACK_SUBAGENT_HOST_MAX=3` caps concurrent claude children host-wide (env in the unit; per-wolf override in `wolfd@<n>.service.d/limits.conf`, written by `provision-wolf.sh <name> [mem] [subagent-max]`). Budget: hubd 105 + workerd(-wolves) 105 + wolfd up to 700 = ~910 MiB for Hal, leaving room for the OS and a second wolf only if its cap is lowered. Hitting MemoryMax OOM-kills inside that wolf's cgroup only; `Restart=on-failure` brings it back and durable state resumes the turn.

## claude-stateless session state
Lives at `<dirname(WOLF_DEN)>/claude-stateless/<basename(den)>` = `/home/wolf-<n>/claude-stateless/den` (wolf.yaml sits in the home, den = `~/den`). It is inside the bind-mounted, writable home; `provision-wolf.sh` creates `~/claude-stateless`. It is rebuildable scratch (resumable claude session files); losing it loses only claude-side context caches, not the thread (thread history is in `den/session.sqlite`).

## Backups (recommendation)
Back up per wolf, from the outside (a root timer, not the wolf): `den/` (**`session.sqlite`+`-wal`+`-shm`, taken with `sqlite3 .backup` or `VACUUM INTO`, not a raw copy of a live db**), `wolf.yaml`, `agent/` (identity), `.env` (separately, encrypted: it holds the token; the token is also re-creatable with `claude setup-token`). Skip `release/` (reproducible from the tarball), `claude-stateless/` and `work/` caches unless the workspace holds unpushed work. Daily snapshot + a DO droplet snapshot weekly; keep `den/backups/` (pre-upgrade store copies written by `backupSessionStore`) as is. Restore = stop `wolfd@n`, put the files back, start.

## Validation status
* `check-units.sh`: units carry the required hardening; link-only unit unchanged.
* **No systemd run here**: this sandbox's Docker cannot `apt-get`/`dnf` (all package mirrors are served through a TLS proxy with an untrusted CA, so signature/cert checks fail; I did not disable them) and no arm64 systemd image was pullable, so `systemd-analyze verify/security` and a booted `workerd-wolves` → `wolfd@hal2` were **not run**. `Dockerfile.systemd` (debian + systemd + polkit, `docker run --privileged`) is ready for a host with working apt; expected checks: `systemd-analyze verify infra/wolves/*.service`, `systemd-analyze security wolfd@hal2`, `systemctl show -p MemoryMax wolfd@hal2`, `ps -o user -C node`.
* `run-sim.sh` (tracer image, real users, `systemctl` double playing PID 1 + polkit): workerd as `workerd-wolves` supervises wolf `hal2` whose wolfd runs as `wolf-hal2`; `workerd-wolves` cannot read `/home/wolf-hal2/.env`; another wolf user cannot list the home; workerd stop leaves wolfd running and the new workerd adopts it; `kill -9 wolfd` is recovered. This validates our scripts and the workerd change, **not** systemd's sandboxing or MemoryMax.
